## Unicode text metadata and encoding compatibility

- Preserve all 1.0.1 connection-string, Unicode initialization, metadata and
  encoding diagnostic fixes.
- Report STRING, JSON, VARCHAR and complex text results as SQL_WVARCHAR,
  and CHAR as SQL_WCHAR, so metadata-driven applications can select Unicode
  fetching. Explicit SQL_C_CHAR still follows ClientCharset.
- Report BINARY as SQL_VARBINARY so binary consumers can retrieve raw bytes.
  DECIMAL remains represented as a numeric string for compatibility.
- Return character column attributes as UTF-16 from W APIs, with full byte
  lengths, safe truncation, SQLSTATE 01004 and invalid-length diagnostics.
  Keep native MaxCompute type names consistent with SQLColumns.
- Keep SQLGetData UTF-16 segments contiguous across surrogate boundaries,
  avoiding inserted NUL characters when clients reassemble long Unicode text.
  Bound buffers and metadata still truncate at complete character boundaries.
- Do not advertise unverified SQL CONVERT capability bits.
- Report 1.0.2 consistently in the MSI, DLL and ODBC driver metadata.

## Trying the update in Power BI

Install the x64 MSI, restart Power BI, and refresh the affected query. Try
without a ClientCharset override first. If a narrow-character consumer expects
GBK, ClientCharset=GBK remains supported.

To diagnose a remaining issue, create C:\Temp and append
LogLevel=INFO;LogPath=C:\Temp\maxcompute-odbc.log; to the full connection string.
Collect the [ODBC-Encoding] lines, Power BI version, and a non-sensitive example
of expected/actual text. SQL_C_WCHAR uses UTF-16; SQL_C_CHAR uses ClientCharset.
These driver fixes do not yet establish that the customer's original Power BI
case is resolved; the update is available for that verification.

[Encoding troubleshooting](https://github.com/aliyun/alibabacloud-maxcompute-odbc-driver/blob/v1.0.2/docs/encoding-troubleshooting.md)
